Report Generation System — Final Consolidated Spec

There are two servers: Server 1 is the production application (Node.js, PostgreSQL, BullMQ, pdfmake) hosting the Script Box, Event Page with Reports Tab, eligibility sync, and WhatsApp consent flow, and Server 2 is a separate GPU-enabled server running the Hermes agent, which calls the qwen3.5:4b model for both report generation and content validation; Server 1 and Server 2 sit on different networks and can only reach each other through a Netbird tunnel — a private, secure connection that nothing on the public internet can access, with every request travelling through this tunnel and hitting a Gateway on Server 2 that checks an API key on every request before forwarding it internally to Hermes, so the model server itself is never exposed directly; if Server 2 is i45G-operated infrastructure this is internal processing needing no new disclosure, but if it is rented GPU or any third-party box it is a processor that must be named in the consent documents, and this needs confirming before the first live batch. In the Script Box, admins upload a fixed Script Prompt template that does not change mid-batch or mid-run, though admins alone can edit it when needed; script prompts are versioned as append-only rows with the version ID pinned at batch creation, so a report generated months ago remains reproducible against the exact template that produced it. On the Event Page's Report Tab, the admin selects an Assessment Form from a dropdown; each form has a single corresponding Answer CSV generated on student completion, and selecting the Form automatically selects its corresponding CSV with no manual step, while the Script Prompt is chosen separately from its own dropdown. The admin sets eligibility criteria (e.g. completion %) and clicks Sync Eligibility, a database check only with no model call, with opted-out students excluded at this stage so they are never enqueued in the first place; eligible students then receive a WhatsApp consent request using quick-reply Yes/No buttons rather than free text, which removes ambiguity at the source, with a 48-hour timeout and a reminder at 24 hours — a non-response is marked no_response, distinct from declined, so batch-yield analysis can tell the two apart; a reply that still doesn't parse gets one clarification prompt before falling through to no_response; consent is never inferred from silence, since DPDPA requires it to be an affirmative act. Students who reply Yes are added to a single shared queue — not separate queues per audience, since splitting would multiply GPU pressure exactly when batches overlap, which is the case the system needs to support; fairness between concurrent batches (e.g. college vs. SME) is handled by interleaving at enqueue time or rate-limiting per organization rather than splitting the queue. "Batch" here means many isolated, single-student requests running concurrently through worker-level concurrency, never multiple students' data combined into one model call; concurrency starts at 2–4 workers and is tuned by measurement, noting that each report involves two model calls (generation plus content validation), so effective GPU load is double the report throughput, and it's worth benchmarking whether the shorter content-validation pass can run at higher concurrency than generation. For each student, the app sends [Questions + CSV answers + Script Prompt] through the tunnel and Gateway to Hermes, which calls qwen to generate the report as JSON matching the schema (student name, issue date, intro message, dimensions with a tier of Strength/Developing/Focus Required/Blind Spot, strengths, focus areas, blind spots, single priority), using schema-constrained decoding so the model is guided toward valid structure during generation rather than relying solely on catching errors afterward — generation remains the one non-deterministic step in an otherwise deterministic pipeline, so a nonzero failure rate here is expected by design, which is why validation exists downstream. Structural validation then checks the JSON mechanically matches the schema — required fields, correct types, tier values restricted to the four allowed labels, valid JSON — without judging whether the content is true; on failure it's sent back for regeneration with the original inputs plus the specific error, on an increasing wait, capped at 2–3 regenerations. Failures are split into two separately tracked budgets: infrastructure failures (network drop, tunnel failure, Gateway/API-key failure) get 3 fast retries at roughly 2s/8s/30s with jitter, while structural or content validation failures get 2–3 slower regenerations, and an infra retry never increments the validation counter or vice versa; a circuit breaker sits on top of this — after N consecutive Gateway failures the queue pauses and alerts instead of draining hundreds of jobs against a dead tunnel. JSON that passes structural validation goes back through the same tunnel and Gateway to Hermes for content validation, where qwen checks for hallucinations, unsupported claims, and correct tier assignment against the rubric, under the same retry-and-cap and failure-type separation, because a report failing the same check for the same reason — bad rubric logic, broken input data — will never pass no matter how many times it's regenerated, and retrying forever would hide that root cause instead of surfacing it. Failures are automatically grouped by error signature rather than reviewed per student, so an admin sees categories like "42 students failed on missing tier field," with the frequency of a signature across a batch distinguishing an isolated data problem from a systemic rubric or prompt problem without manual judgment; once a report exhausts its retry cap it's marked failed in the database rather than stopping silently, with no per-student notification — the batch owner is notified once on batch completion with the grouped summary, and a real-time alert fires only on threshold breach (failure rate above roughly 10%, or circuit breaker open); manual re-trigger is available, scoped to an error-signature group rather than the whole batch, so fixing one rubric line doesn't regenerate reports that were already fine. JSON that passes both checks is converted into a PDF by pdfmake and sent over WhatsApp, with delivery split into two jobs with separate states to guarantee idempotency: the PDF is generated to content-addressed storage keyed on a hash of the validated JSON, so regeneration after a crash is free and deterministic; before calling WhatsApp, a delivery_attempt row is inserted with a unique constraint on (report_id, channel), so a duplicate insert means someone already sent it; the provider message ID is recorded after the call returns; and on recovery, an attempt row with no provider ID is reconciled against the provider's message status rather than resent blind. Because a student's 24-hour WhatsApp session window opens on their Yes reply, a batch stuck behind GPU capacity risks landing generation outside that window and failing the send — this needs either an approved template message for delivery or a queue SLA guaranteeing generation completes within 24 hours of consent, decided before the first large batch runs. For every report, the audit trail stores the pinned prompt version ID, model name and tag, a hash of the input row, the raw response from both model passes, validation errors, retry counts by type, the Gateway request ID, and timings, with raw model response retention kept shorter than the report's own retention. On consent withdrawal, the PDF and generated JSON are deleted but a tombstone row (report ID, student ID, deleted timestamp, reason) is kept as proof of deletion; re-requesting a report after an initial decline is allowed; declined and opted_out are kept as distinct states, since declining one report isn't a request to stop all future messaging. Retention is concrete and enforced by a scheduled job, not left as a policy nobody automated: Answer CSVs and student responses for the life of the programme record then anonymized around 12 months, generated JSON for 90 days after successful send, PDFs for 90 days after delivery unless re-download becomes a product feature, raw model responses and audit rows for 90 days, and operational logs for 30 days. For minors — the highest-risk item, and one to run past counsel before building — date of birth is captured at enrolment rather than inferred from the cohort; the entire flow, both the Yes/No prompt and PDF delivery, goes to a verified guardian number rather than the student's own; the guardian relationship and how consent was verified are recorded; no guardian number means no generation, failing closed rather than defaulting to the student; and for institutional batches, the institution may collect and reference guardian consent at enrolment but cannot consent on the guardian's behalf. Finally, opt-out is enforced through a student-level suppression flag checked at every send point, applied twice — excluded during eligibility sync so opted-out students are never enqueued, and re-checked again at send time in case someone opts out mid-batch — with WhatsApp's own block/stop signals honoured as an opt-out event, and the suppression record itself is never deleted even though the underlying report data may be, since opt-out is not the same as deletion and can't be enforced without a surviving record.

Open items still requiring confirmation: Server 2's hosting/operator status for consent-document disclosure purposes; whether generation can reliably finish inside the WhatsApp 24-hour session window at real batch volume or needs a template-message fallback; legal review of the minors' consent flow before implementation; and the actual GPU-sustainable concurrency number, to be benchmarked rather than assumed.
